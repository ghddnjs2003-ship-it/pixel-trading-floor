# 서버 백엔드 — AI 두뇌 · v7 룰 엔진 · 백테스트 · 킬스위치

브라우저 데모는 그대로 두고, **실전 매매 직전에 필요한 서버 쪽 부품**을 여기 모았다.
키는 모두 이 디렉터리의 `.env`에만 둔다(브라우저로 내려가지 않는다. `.env`는 git 무시).

```
backend/
  config.py        환경변수 → 제공자/전략/킬스위치 설정
  providers.py     OpenAI 호환 어댑터 (Groq·Gemini·OpenRouter·Cerebras·Ollama·OpenAI·xAI 공용)
  orchestrator.py  13인 분석 흐름 + v7 규칙 문맥 + 킬스위치 게이트
  server.py        정적 파일 서버 + /api/analyze · /api/stream(SSE)
  strategy.py      더블 S + MDS v7 룰 엔진 (파인스크립트 v7의 판정 부분 1:1 이식)
  backtest.py      과거 캔들 백테스트 (수수료·슬리피지·손절 우선 체결, 반익·추적 청산)
  explore.py       백테스트 조합 탐색 (손절·목표·필터 조합 표 + 인샘플/아웃샘플)
  label_audit.py   차트 라벨 ↔ 엔진 신호 봉 단위 대조
  risk.py          킬스위치 (일일 손실·연속 손절·과매매·급변·수동 정지)
  test_*.py        단위 테스트 38개 (python3 -m unittest discover backend)
```

## 1. AI 두뇌 — 무료 API 먼저, 로컬 Ollama는 나중에

`LLM_PROVIDER` 한 줄로 갈아 끼운다. 모두 OpenAI 형식(`/chat/completions`)을 쓰므로 코드는 그대로다.

| 제공자 | 필요한 키 | 무료 여부 | 기본 모델 |
|---|---|---|---|
| `groq` | `GROQ_API_KEY` | 무료 한도 | `llama-3.3-70b-versatile` |
| `gemini` | `GEMINI_API_KEY` | 무료 한도 | `gemini-2.0-flash` |
| `cerebras` | `CEREBRAS_API_KEY` | 무료 한도 | `llama-3.3-70b` |
| `openrouter` | `OPENROUTER_API_KEY` | `:free` 모델 | `meta-llama/Llama-3.3-70B-Instruct:free` |
| `ollama` | **없음** | 로컬 GPU | `qwen2.5:7b-instruct` |
| `openai` / `xai` | 각각의 키 | 유료 | `gpt-4.1-mini` / `grok-3-mini` |

- `LLM_PROVIDER=auto`면 무료 제공자 → 유료 → Ollama 순으로 **키가 있는 첫 곳**을 쓴다.
- `LLM_MODEL`, `LLM_BASE_URL`로 모델·주소를 덮어쓸 수 있다(새 모델·자체 서버 대응).
- 어떤 제공자가 준비됐는지 확인: `python -m backend.providers`

```bash
cp backend/.env.example backend/.env      # 무료 키 하나만 채우면 된다
python -m backend.providers               # 키 유무 표
python -m backend.server                  # http://127.0.0.1:8765/index.html?engine=llm
```

13인 흐름은 호출 1회당 13번의 LLM 요청을 낸다. 무료 한도가 작은 제공자는 하루 몇 번이면
말라붙으니, `orchestrator`에 규칙 판정(v7)을 먼저 넣어 **AI가 볼 자료를 줄이고**,
실전 판단은 규칙 엔진이 하고 AI는 해설·예외 검토를 맡는 순서가 현실적이다(현재 코드가 그 구조).

## 2. v7 룰 엔진 (`strategy.py`) — 차트 라벨과 봉 단위로 맞춘다

트레이딩뷰 통합 지표 `indicators/double-s-mds-v7.pine`의 **판정 부분**을 파이썬으로 옮겼다.
라벨·박스 그리기는 옮기지 않았다(화면은 파인스크립트가 한다).

**2026-11-19 재이식.** 초안이 파인과 달랐던 곳을 실제 차트 라벨과 대조해 고쳤다.

| 항목 | 초안(폐기) | v7 파인 그대로(현재) |
|---|---|---|
| 스윙 레벨 | 24봉 2봉 프랙털, 가격 위/아래로 필터 | `ta.pivothigh/low(10,10)` + 배열 최대 5개(소모된 레벨도 자리를 차지) |
| BOS | 회복 봉이 직전 봉 구조를 깨야 함(기본 ON) | **없음** — 파인에 없는 조건이라 신호를 지우고 있었다 |
| 매물대 존 | 거래량 프로파일(192봉·60칸) | **1시간봉 몸통 피벗(좌우 5) ± 0.30 × 1H ATR**, 방향별 3개 |
| 존 확정 | 4봉 나이 | 이탈 + 4봉, 또는 60봉(파인 `boxExitBuf`·`maxBoxBars`) |
| M1 리테스트 | 15봉, 첫 리테스트 | 8봉, 0.15 ATR 터치, 15봉 쿨타임, 방향별 연속 2회 제한 |
| 볼린저 | 종가 표준편차 폭 비교 | `(상단-하단)/중심×100` 폭이 **10봉 평균보다 큰지** |
| 손익비 | 1.5R 미만 신호 폐기 | 라벨은 그대로 두고, 목표만 반대편 유동성→1.5R 대체 |

- 스윕: 깊이 0.05~1.60 ATR + 같은 봉 거부(종가 복귀) 또는 다음 봉 복귀, 0.5 ATR 완전 돌파 시 레벨 폐기
- 추세 필터: EMA20/EMA50 + 3연속 음봉·양봉 (파인 `isStrongUp/isStrongDown`)
- M1: 존 경계를 거래량 1.15배로 종가 돌파 → 첫 리테스트에서 경계 유지 + CCI(20, hlc3) 방향 + 볼린저 확장 + 리테스트 거래량 감소
- 손절: M1은 존 반대편 경계(파인 `m1Stop`), 더블 S는 스윕 극점 밖 0.15 ATR(CES 룰 — 파인에 없는 값)
- 신호는 i번 봉이 끝난 뒤 확정, 진입은 i+1 시가(미래 참조 없음 — 테스트로 고정)

### 차트 라벨 1:1 대조 결과 (2026-11-19)

`python -m backend.label_audit --json data/btc_15m_3600.json --expected data/chart_labels_2026-11-19.txt --from "11-10 00:00" --to "11-19 11:30"`

- 데이터: 바이비트 `BTCUSDT.P` 15분봉 대신 **비트겟 BTCUSDT 15분봉**(이 환경에서 바이비트 API는 403, 바이낸스는 451). 가격 차이는 보통 $1~20.
- 결과: **일치 8/10**. 11-16 15:00~11-19 11:30 화면에 보이는 라벨 5개 중 3개 일치, 그 구간에 **화면에 없는 엔진 라벨 0개**.
- 살아 있는 레벨·존도 화면과 거의 같다: 차트 `저항 64720.3~64988.4 확정` ↔ 엔진 `64,709.4~64,982.6 확정`, `SSL 73,500.0` ↔ 엔진 `73,503.7`, `BSL 75,228.4` ↔ 엔진 `75,228.3`.

남은 2건은 규칙 차이가 아니라 **거래소 데이터 차이로 임계값이 갈린 경계 사례**다.

| 화면 라벨 | 엔진 | 막은 조건(비트겟 데이터) | 확인 |
|---|---|---|---|
| 11-17 07:30 `▲ M1 롱` | 없음 | 돌파봉 거래량 276 = 20봉 평균 276. 필요 1.15배(317.5) | `volume_mult=0.95`로 낮추면 **정확히 07:30에 M1 롱** 발생 |
| 11-18 01:00 `▲ 롱·거부` | 없음 | 추세 필터 `close > high[1]`: 종가 64,178.8 vs 직전봉 고가 64,210.7 (약 $32 부족) | 필터를 끄면 01:00에 발생(대신 00:45·07:45·15:30·23:30 오탐 4건이 함께 생김 → 필터가 필요한 이유) |

## 3. 백테스트와 조합 탐색 (`backtest.py` · `explore.py`)

```bash
python -m backend.backtest --symbol BTCUSDT --limit 3000 --source bitget
python -m backend.backtest --json-in data/btc_15m_3600.json --kind DS --target r:2.0
python -m backend.explore  --source bitget --limit 8200           # 조합 표 + 인샘플/아웃샘플
python -m backend.explore  --json data/btc_15m_3600.json          # 저장해 둔 캔들로 같은 실험
```

- 데이터: 바이비트·OKX·비트겟·바이낸스 공개 API(키 불필요) 또는 저장한 CSV/JSON. `auto`면 되는 곳부터.
- 체결: 다음 봉 시가, 손절·목표가 같은 봉에서 둘 다 닿으면 **손절 우선**(비관), 편도 수수료 5bp·슬리피지 2bp 기본.
- 청산: `--exit-mode bracket`(전량 목표) 또는 `half_trail`(1R 절반 익절 + 본전 + ATR 추적).
- 지표: 체결 수·승률·평균 R·PF·순손익·최대낙폭·최장 연속손실·종류별.

### 실측 (BTCUSDT 15분봉 8,200봉 = 2026-08-25~11-19, 85일, 80,632 → 62,449 / −22.6% 구간)

8,200봉 파일은 저장소에 넣지 않았다. 위 명령으로 비트겟에서 다시 받는다(2026-11-19 12:00 KST 기준).

계좌 10,000 USDT · 거래당 1% 리스크 · 수수료 5bp · 슬리피지 2bp.

| 조합 | 체결 | 승률 | PF | 순손익 | MDD |
|---|---|---|---|---|---|
| 더블S 단독 | 78 | 16.7% | 0.29 | −47.0% | 48.0% |
| M1 단독 | 63 | 25.4% | 0.29 | −34.0% | 36.4% |
| 통합(기본) | 101 | 19.8% | 0.28 | −53.5% | 54.9% |
| 목표 2.5R (더블S) | 78 | 24.4% | 0.50 | −33.8% | 35.9% |
| M1 손절 버퍼 0.15 ATR | 62 | 33.9% | 0.50 | −22.2% | 24.3% |
| M1 + 4H EMA200 | 26 | 38.5% | 0.56 | −8.5% | 12.0% |
| 롱만 + 4H EMA200 | 37 | 32.4% | 0.52 | −14.4% | 17.6% |
| 반익+본전+ATR추적 | 141 | 27.7% | 0.13 | −64.8% | 65.4% |

**결론: 이 구간에서 기계적 체결은 어떤 조합도 플러스가 아니다.** 표본 26~141건, 인샘플(앞 60%)·아웃샘플(뒤 40%) 모두 마이너스로 같은 방향이다.

- 비용을 0으로 두면 더블S −27.0%, M1 −20.0% — **비용 전에도 마이너스**다. PF 0.28→0.48 수준.
- 롱·숏 양쪽 다 진다(더블S 롱 12.5% / 숏 21.1% 승률). 하락 구간 탓만은 아니다.
- 구조적 이유: 손절이 스윕 극점 밖이라 위험 폭이 1R≈2 ATR까지 벌어진다. 1.5R 목표는 3 ATR 이상 떨어진 자리이고, 15분봉에서 그만큼 밀어주는 경우가 드물다. 손절을 1 ATR로 좁히면 승률은 43%까지 오르지만 PF 0.72로 여전히 손익분기 아래다.
- 가장 덜 나쁜 조합은 **M1 + 4H EMA200 + 1R 목표** — 비용 0에서 27건·승률 51.9%·PF 1.07·+0.9%로 겨우 본전. 비용을 넣으면 사라진다.
- 반익(1R 절반) + 추적은 승률을 39%로 올리지만 PF가 0.13~0.35로 가장 나빠진다. 이기는 추세를 절반에서 잘라 먹고, 남은 절반은 추적 손절에 걸리기 때문이다.
- 4H EMA200을 더블S에도 요구하면 거래가 78→29건으로 줄고 순손익 −47.0%→−20.1%로 개선되지만 플러스는 아니다.

**이 숫자를 근거로 실돈을 넣지 않는다.** 다음에 확인할 것: ① 세션·시간대 필터(아시아/런던/뉴욕) ② 손절을 구조(스윕 극점)가 아니라 변동성 고정으로 두고 목표를 1R로 ③ M1만 + 4H 추세 정렬 ④ 청산 규칙을 '반대편 존 도달'로 두고 표본을 6개월로 늘리기.

### 과최적화 경계

- 조합을 30개 넘게 돌렸으니 그중 하나쯤 잘 나오는 것은 당연하다. 그래서 (a) 체결 10건 미만 조합은 표에서 제외하고 (b) 인샘플에서 고른 조합의 아웃샘플 성적을 함께 냈고 (c) 비용·체결 가정을 모든 조합에 똑같이 적용했다.
- 인샘플 상위 조합이 아웃샘플에서 뒤집히는 경우가 많았다(예: `목표 2.5R 더블S` IS −9.5% → OS −24.3%). 조합 선택 자체가 과최적화라는 뜻이다.

## 4. 킬스위치 (`risk.py`)

AI·규칙과 분리된 정지 장치. 주문은 내지 않고 "지금 진입해도 되나"만 답한다.

| 규칙 | 기본값 | 동작 |
|---|---|---|
| 일일 최대 손실 | 계좌의 3% | 당일 중단 |
| 연속 손절 | 3회 | 당일 중단(쿨다운 30분 뒤 재개) |
| 일일 거래 수 | 20회 | 당일 중단 |
| 급변 | ATR ≥ 가격의 2.5% | 30분 일시 중단 |
| 자본 하한 | 시작 자본의 90% | 사람 확인 전까지 중단 |
| 수동 정지 | — | 직접 풀기 전까지 진입 금지 |

- 상태는 `backend/state/killswitch.json`에 남고 KST 자정에 자동 초기화된다(수동 정지는 유지).
- `orchestrator`는 최종 판정 직전에 이 게이트를 본다 — 막혀 있으면 AI가 매수를 골라도 HOLD로 바꾸고 이유를 남긴다.
- 환경변수: `KILL_DAILY_LOSS_PCT`, `KILL_MAX_CONSECUTIVE_LOSSES`, `KILL_MAX_DAILY_TRADES`,
  `KILL_VOLATILITY_ATR_PCT`, `KILL_COOLDOWN_MINUTES`

## 5. 아직 없는 것 (일부러 만들지 않음)

- **거래소 주문 전송**: 실돈이 나가는 일이라 사용자 결정 없이 붙이지 않는다. 붙일 때는
  API 키 권한을 출금 불가·선물 거래만으로 좁히고, `risk.py` 게이트를 반드시 앞에 둔다.
- 실시간 루프(24시간 구동): 지금은 백테스트·판정까지. 루프를 돌리려면 PC 상시 구동과
  거래소 키가 먼저 필요하다.
- **5분봉 라이브 판정의 존**: orchestrator는 5분봉 144개(12시간)만 받는다. 1시간봉 몸통 피벗은
  최소 11시간 + 확인 1시간이 필요해 그 창에서는 존이 거의 서지 않는다. 라이브에서 M1까지 보려면
  수집 봉 수를 1,000개 이상으로 늘려야 한다.
